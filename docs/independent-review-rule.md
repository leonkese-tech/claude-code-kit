# "고친 쪽이 아닌 다른 눈이 다시 본다" — 에이전트 수정 뒤 독립 재검수

**TL;DR (EN):** When an agent fixes code, "its tests pass" says little about side effects. In one small batch of first-pass fixes, a second, independent reviewer found a new defect in more than half of them while the test suite was fully green. The weakness is not knowledge but not seeing the side effects of your own change.

## 상황

전문가 에이전트(도메인별로 규칙을 들고 있는 하위 에이전트)가 코드를 고치고 "테스트 통과"를 보고했습니다. 같은 기간 규칙 이해도 시험도 전부 통과였습니다. 그런데 작은 표본(첫 수정 6건)에서 **절반을 넘는 건**에서 다른 검수자가 새 결함을 찾았습니다.

공통점은 고친 곳은 맞는데 **옆에서 깨진 것**입니다(다른 경로의 회귀, 경보가 가려지는 부작용, 가드 한 줄이 무력화되는 수정 같은 유형). 고친 쪽의 테스트는 자기가 본 경로만 확인합니다.

## 규칙

1. 코드를 고친 쪽과 **다른** 검수자가 그 커밋을 다시 읽고 **재현**해 본 뒤에 완료로 봅니다.
2. 고친 쪽의 "테스트 통과"는 재검수를 대신하지 않습니다.
3. 고친 쪽의 보고에는 **기댄 가정**("이게 틀리면 무엇이 깨지는가")을 적게 하고, 검수자는 그 미확인 가정부터 깹니다.
4. 검수자가 하나라도 결과 없이 끝나면 "깨끗함"이 아니라 **검수 미완료**로 취급합니다.
5. 재검수는 최대 3회로 끝냅니다. 3회차에 새 결함이 없으면 남은 것은 "알려진 잔여"로 문서화합니다. 같은 부류의 결함이 두 회 반복되면 규칙을 더 고치지 말고 **줄이는 쪽(삭제·가드)** 으로 갑니다.
6. 입력을 보고 "바꿀지·고를지" 정하는 규칙(맞춤법·분류·판독)은 구현 전에 **정답 데이터(오라클)** 부터 만들고, 변형 전수 시험에서 오교정 0이 아니면 병합하지 않습니다. 틀린 변경이 사람에게 나가는 것이 못 고치는 것보다 나쁩니다.

## 이 저장소의 `expert-task-generic.js`

위 1~5번을 Claude Code 워크플로우로 옮긴 것입니다(전문가 구현 → 위험도별 독립 재검수 → 보완 → 재검수). 검수 관점은 공통·도메인·반대 입장·협업 관점으로 나눠서, 모든 검수자가 같은 곳만 보지 않게 합니다.

## 한계

- 6건이라는 표본은 작습니다. 재검수 비용(토큰)이 느는 만큼의 가치가 있는지는 위험도에 따라 정하세요. 위험이 낮은 변경은 한 명으로 충분합니다.
- 검수자도 같은 모델이면 같은 맹점을 공유할 수 있습니다. 가능하면 한 명은 다른 모델이나 다른 지침으로 돌리세요.
